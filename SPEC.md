## 1. Продукт в двух абзацах

Telegram Mini App + бот, который закрывает рутину стендап-индустрии: комики находят выступления и ведут календарь, организаторы набирают составы и собирают подтверждения, ведущие видят актуальный порядок, клубы объединяют несколько организаторов и площадок.

Ядро MVP — **один полный цикл мероприятия**: организатор создаёт событие → набирает комиков (заявки / ссылка / приглашения) → утверждает состав и порядок → в день выступления бот собирает подтверждения → организатор и ведущий видят, кто точно придёт, и при необходимости ставят замену из резерва.

Роли: **комик**, **организатор**, **ведущий** (у одного пользователя может быть несколько ролей), **клуб** (организация, вне MVP).

Рынки: Россия и Казахстан. Валюты: ₽ и ₸ (оплаты вне MVP).

## 2. Стек и структура

TypeScript везде.

| Слой | Технология |
|---|---|
| Монорепо | pnpm workspaces |
| Бэкенд API | Node.js 20+, Fastify, Zod (валидация), Drizzle ORM |
| БД | PostgreSQL 16 |
| Очереди / кэш | Redis + BullMQ (только для отправки сообщений с троттлингом) |
| Бот | grammY |
| Mini App | React 18 + Vite, `@telegram-apps/sdk-react`, TanStack Query, React Router |
| Хранилище файлов | S3-совместимое (в dev — MinIO) |
| Тесты | Vitest; интеграционные тесты против реального Postgres в Docker |
| Локальный запуск | docker compose |

Структура:

```
/apps
  /api        — Fastify HTTP API
  /bot        — grammY бот (webhook в prod, long polling в dev)
  /worker     — планировщик уведомлений + отправка (BullMQ)
  /miniapp    — React Mini App
/packages
  /db         — схема Drizzle, миграции, сиды
  /domain     — чистая бизнес-логика без I/O (статусы, пересечения, права, расписание уведомлений)
  /shared     — типы, Zod-схемы API, тексты i18n
/docs
  PROGRESS.md
```

Правило: **вся бизнес-логика — в `packages/domain`** в виде чистых функций. API, бот и воркер только вызывают её и работают с БД. Это делает логику тестируемой без Telegram и без базы.

## 3. Модель данных

Все времена — `timestamptz` (хранится UTC). У каждой площадки есть IANA-таймзона, отображение — всегда в таймзоне площадки.

### users
- `id` uuid PK
- `telegram_id` bigint unique
- `telegram_username` text null
- `first_name`, `last_name` text
- `language_code` text
- `timezone` text — IANA, по умолчанию берётся из города профиля
- `bot_started` bool — запускал ли пользователь бота (без этого бот не может ему писать)
- `bot_blocked` bool — получили 403 при отправке
- `created_at`, `updated_at`

### user_roles
- `user_id`, `role` enum(`comedian`, `organizer`, `host`) — PK (user_id, role)

### cities
- `id`, `name`, `country` enum(`RU`, `KZ`), `timezone` (IANA)
- Сиды: крупные города РФ и КЗ с правильными таймзонами.

### comedian_profiles
- `user_id` PK FK
- `stage_name` text **обязательное**
- `city_id` FK
- `category` enum(`newbie`, `experienced`, `media`) — самоопределение
- `category_verified` bool default false — задел под модерацию (вне MVP)
- `bio` text null
- `contact` text **обязательное** (телефон / @username — для связи организатора, если не отвечает в боте)
- `links` jsonb — массив `{type, url}` (видео выступлений, соцсети)
- `travel_buffer_minutes` int default 30 — сколько нужно между площадками
- `default_set_minutes` int null
- `is_searchable` bool default true

### comedian_photos
- `id`, `user_id`, `s3_key`, `width`, `height`, `sort_order`, `created_at`
- Ресайз при загрузке: оригинал + превью 400px. Лимит 10 фото, 10 МБ на файл.

### organizer_profiles
- `user_id` PK, `display_name`, `project_name`, `city_id`, `contact`

### venues
- `id`, `name`, `address`, `city_id`, `timezone`, `lat`/`lng` null (под расчёт дороги, вне MVP), `created_by`

### events
- `id`
- `organizer_id` FK users
- `venue_id` FK
- `title`, `format` enum(`open_mic`, `showcase`, `concert`, `other`) + `format_note` text null
- `starts_at` timestamptz, `ends_at` timestamptz null
- `slots_count` int — сколько комиков в составе
- `set_minutes` int — длительность сета по умолчанию
- `gap_minutes` int default 2 — пауза между сетами
- `conditions` text — условия участия (оплата, взнос, требования)
- `recruitment_open` bool — видно в общем списке, можно подать заявку
- `recruitment_link_token` text null unique — запись по ссылке
- `status` enum(`draft`, `recruiting`, `lineup_locked`, `finished`, `cancelled`)
- `lineup_version` int — для оптимистической блокировки при изменении порядка
- `created_at`, `updated_at`

Адресные приглашения возможны в любом событии, флага не требуют. Способы набора совмещаются.

### participations — заявки и приглашения в одной сущности
- `id`
- `event_id` FK, `comedian_id` FK users — unique(event_id, comedian_id)
- `source` enum(`application`, `link`, `invitation`)
- `status` enum — см. раздел 4
- `position` int null — номер в составе (только для `accepted`)
- `set_minutes_override` int null
- `invited_by` FK null
- `auto_accepted` bool default false
- `counter_proposal` text null — «предложить другое время» (свободный текст в MVP)
- `day_confirmation` enum(`none`, `confirmed`, `declined`) default `none`
- `day_confirmed_at` timestamptz null
- `attendance` enum(`unknown`, `present`, `absent`) — отмечает ведущий/организатор
- `created_at`, `updated_at`
- **История:** таблица `participation_events` (id, participation_id, actor_id, from_status, to_status, payload jsonb, created_at) — пишется на каждый переход.

### event_staff — ведущие
- `event_id`, `user_id`, `role` enum(`host`)
- `permissions` jsonb — набор флагов: `can_reorder`, `can_mark_attendance`, `can_call_reserve`, `can_notify_lineup`
- PK (event_id, user_id)

### busy_slots — ручная занятость и ручные события комика
- `id`, `user_id`, `starts_at`, `ends_at`, `title` text null, `kind` enum(`busy`, `manual_gig`), `venue_text` null, `created_at`

### auto_accept_rules
- `id`, `comedian_id`
- `organizer_id` — доверенный организатор (одно правило на организатора)
- `formats` enum[] null — null = любые
- `weekdays` int[] null, `time_from`/`time_to` time null — окно, в которое можно принимать
- `max_gigs_per_day` int null
- `enabled` bool
- `created_at`

### scheduled_notifications
- `id`, `user_id`, `kind` enum (см. раздел 7), `participation_id` null, `event_id` null
- `send_at` timestamptz
- `status` enum(`pending`, `sent`, `cancelled`, `failed`)
- `dedupe_key` text unique — например `day_digest:{user_id}:{date}`
- `attempts` int, `last_error` text null, `created_at`

### telegram_chats — чаты, куда бот может постить анонсы
- `id`, `telegram_chat_id` bigint unique, `title`, `type`, `added_by` FK users, `bot_can_post` bool, `created_at`

### event_posts
- `id`, `event_id`, `chat_id`, `telegram_message_id`, `created_at` — чтобы обновлять пост при изменениях

### calendar_feeds
- `user_id` PK, `token` text unique (случайные 32 байта, base64url), `created_at`, `revoked_at` null

## 4. Статусы участия

```
application/link:  pending ──accept──▶ accepted
                   pending ──reject──▶ rejected
                   pending ──reserve─▶ reserve ──promote──▶ accepted
invitation:        invited ──comedian accepts──▶ accepted
                   invited ──comedian declines─▶ declined
                   invited ──counter-propose──▶ counter_proposed ──organizer accepts──▶ accepted
                                                                 ──organizer rejects──▶ declined
любой активный:    ──comedian withdraws──▶ withdrawn
                   ──organizer removes──▶ removed
accepted:          ──moved to reserve──▶ reserve
```

Статусы: `pending`, `invited`, `counter_proposed`, `accepted`, `reserve`, `rejected`, `declined`, `withdrawn`, `removed`.

Правила:
- Переходы описаны **одной таблицей разрешённых переходов** в `packages/domain/participation.ts` — функция `transition(current, action, actorRole) → next | error`. Всё остальное вызывает её.
- `position` есть только у `accepted`. При выходе из `accepted` позиции остальных уплотняются.
- Нельзя сделать `accepted`, если состав заполнен (`slots_count`) — только в резерв. Исключение: организатор явно увеличивает `slots_count`.
- При переходе в `accepted` **обязательна проверка пересечений** (раздел 6.1). Организатор может принять вопреки предупреждению (явное подтверждение в UI), автопринятие — никогда.
- Каждый переход порождает уведомление участнику (раздел 7) и запись в `participation_events`.

## 5. Права

Функция `can(user, action, resource) → bool` в `packages/domain/permissions.ts`. Покрыть тестами каждую строку таблицы.

| Действие | Комик (участник) | Организатор события | Ведущий события |
|---|---|---|---|
| Видеть событие | если открыто / по ссылке / приглашён | да | да |
| Подать заявку | если открыто или по ссылке | — | — |
| Принять/отклонить приглашение | своё | — | — |
| Принимать/отклонять заявки, резерв | — | да | нет |
| Приглашать комиков | — | да | нет |
| Менять порядок | — | да | если `can_reorder` |
| Отмечать присутствие | — | да | если `can_mark_attendance` |
| Звать резервного на замену | — | да | если `can_call_reserve` |
| Рассылка составу | — | да | если `can_notify_lineup` |
| Редактировать/отменять событие | — | да | нет |
| Назначать ведущего | — | да | нет |

Права клубов — вне MVP, но `permissions` должна расширяться без миграции логики.

## 6. Ключевая логика

### 6.1. Окно выступления и пересечения

Для каждого `accepted`-участия вычисляется **примерное окно на сцене**:

```
start_i = event.starts_at + Σ (set_minutes_j + gap_minutes) для всех j с position < i
end_i   = start_i + set_minutes_i
```

Если позиции ещё нет (статус не `accepted`, или порядок не задан) — окно = всё событие: `[starts_at, ends_at ?? starts_at + slots_count × (set + gap)]`.

**Окно занятости комика** = окно на сцене, расширенное на `travel_buffer_minutes` с обеих сторон.

Конфликт = пересечение окна занятости нового выступления с:
- окнами занятости других его `accepted`-участий,
- его `busy_slots` (без буфера для `busy`, с буфером для `manual_gig`).

Реализация:
- Чистая функция `computeSlotWindows(event, participations)` и `findConflicts(candidateWindow, existingWindows)` в `packages/domain`.
- В БД для поиска кандидатов используй `tstzrange` и оператор `&&`. Индексы GiST по нужным полям.
- Результат проверки — список конфликтов с указанием, с чем именно пересекается (для UI: «Пересекается с: Open Mic в «Подвале», 20:30–20:40»).

Пересчитывать окна при каждом изменении порядка, длительности или времени события. При изменении — заново проверить конфликты у всех участников события и, если появились, уведомить организатора.

### 6.2. Автопринятие приглашений

Когда комику приходит приглашение:
1. Найти включённое правило `auto_accept_rules` для пары (комик, организатор).
2. Проверить условия правила: формат, день недели, окно времени, `max_gigs_per_day`.
3. Проверить пересечения (6.1).
4. Если всё ок и есть свободное место → перевести в `accepted` с `auto_accepted = true`.
5. Иначе → оставить `invited`, комик решает вручную. В уведомлении указать, почему не сработало автопринятие («есть пересечение», «вне вашего окна времени»).

**Гонки:** шаги 2–4 выполнять в одной транзакции с `pg_advisory_xact_lock(hash(comedian_id))`. Тест: два приглашения на одно время приходят одновременно → принято ровно одно.

Организатор видит у участника метку «подтверждён автоматически». Комик может отключить правило в любой момент; уже принятые выступления при этом не отменяются.

### 6.3. Набор и состав

- Открытый набор: событие видно в списке «Ищут комиков» в городе, кнопка «Подать заявку».
- По ссылке: `t.me/<bot>/<app>?startapp=j_<link_token>` → экран события с кнопкой «Записаться». Организатор может перевыпустить токен.
- Адресный: организатор ищет комиков (по имени, городу, категории, «свободен в это время») и приглашает одного или нескольких.
- Экран состава: список `accepted` с позициями (drag-and-drop), резерв, заявки, приглашения в ожидании. Изменение порядка отправляет `lineup_version`; при несовпадении — 409 и перезагрузка списка.
- Обновления у второго редактора — polling каждые 5 секунд на экране состава (WebSocket не нужен).
- **Замена:** организатор/ведущий выбирает выбывшего → предлагаются резервисты (без конфликтов наверху) → «Позвать» отправляет приглашение с флагом срочности. Первый, кто принял, занимает позицию выбывшего.
- **Текст для афиши:** кнопка «Скопировать для афиши» формирует текст: название, дата/время, площадка, адрес, ведущий, состав в порядке выхода (сценические имена + ссылки), условия. Шаблон текста — в i18n.

### 6.4. Уведомления в день выступления

Расписание для каждого `accepted`-участия:

| Когда | Что | Кому |
|---|---|---|
| В день выступления в `digest_time` комика (по умолчанию 10:00 по его таймзоне) | Дайджест: все выступления на сегодня — площадка, время, номер в составе. Кнопки «Прочитал, участие подтверждаю» / «Не смогу» | комику |
| Через 2 часа без ответа | Повторное напоминание | комику |
| За 3 часа до начала без ответа | «Не подтвердил: имя, контакт» + кнопка «Позвать резерв» | организатору и ведущему |
| За N минут до примерного выхода (по умолчанию 30, настраивается, можно выключить) | Напоминание | комику |
| Нажал «Не смогу» | Мгновенно: «Имя снял участие» + кнопка «Позвать резерв» | организатору и ведущему |

Один дайджест на комика в день, даже если выступлений несколько (`dedupe_key`).

Если событие создано или участник принят **после** времени дайджеста в день события — отправить дайджест сразу.

## 7. Уведомления и бот

### 7.1. Архитектура
- Источник правды — таблица `scheduled_notifications`.
- **Планировщик** (`apps/worker`): тик раз в минуту, выбирает `pending` с `send_at <= now()` (`FOR UPDATE SKIP LOCKED`), ставит задачи в BullMQ.
- **Отправитель**: BullMQ-воркер с троттлингом — не более 25 сообщений/сек суммарно и 1 сообщение/сек в один чат. Ретраи с экспоненциальной паузой. На 429 — уважать `retry_after`. На 403 — `users.bot_blocked = true`, дальше не слать, уведомление `failed`.
- **Пересчёт:** функция `rescheduleForParticipation(id)` и `rescheduleForEvent(id)` — отменяет `pending` и создаёт заново. Вызывается при любом изменении события, состава, статуса или настроек уведомлений комика.
- Расчёт времени отправки — чистая функция в `packages/domain/notifications.ts` с тестами на таймзоны (Москва, Новосибирск, Алматы, Владивосток, Калининград) и на переходы через полночь.

### 7.2. Типы уведомлений (MVP)
`invitation_received`, `invitation_auto_accepted`, `application_accepted`, `application_rejected`, `moved_to_reserve`, `promoted_from_reserve`, `removed_from_lineup`, `event_changed` (время/площадка), `event_cancelled`, `lineup_position_changed`, `day_digest`, `day_digest_repeat`, `unconfirmed_alert` (организатору), `withdrawal_alert` (организатору), `pre_show_reminder`, `replacement_request` (резервисту), `counter_proposal_received` (организатору), `new_application` (организатору, можно агрегировать: не чаще раза в 15 минут на событие).

Каждое сообщение содержит кнопку «Открыть» → Mini App на нужном экране (`startapp=e_<event_id>` и т.п.).

### 7.3. Команды бота
- `/start` — приветствие, `bot_started = true`, кнопка открытия Mini App. Обработать `start` с параметром (переход на событие).
- `/today` — дайджест на сегодня.
- `/settings` — открыть настройки уведомлений в Mini App.
- Callback-кнопки: подтвердить/отказаться (день выступления), принять/отклонить приглашение прямо из сообщения, «Позвать резерв».

### 7.4. Посты в чаты
- Организатор добавляет бота в группу/канал. Бот получает `my_chat_member` → создаёт `telegram_chats` с `added_by`.
- В событии организатор выбирает чаты из тех, что добавил сам, → бот публикует анонс.
- **Важно:** в группах кнопки типа `web_app` не работают. Использовать URL-кнопку на прямую ссылку Mini App: `https://t.me/<bot_username>/<app_short_name>?startapp=e_<event_id>` (Mini App должен быть зарегистрирован в BotFather через `/newapp`).
- При изменении события — редактировать пост (`event_posts`). При заполнении состава — пометка «Набор закрыт».

## 8. Mini App — экраны

Общее:
- Тема — из `themeParams` Telegram (светлая/тёмная), нативные `BackButton` и `MainButton`, хаптика на ключевых действиях.
- Адаптивная вёрстка: телефон и Telegram Desktop (организаторы будут собирать составы с компьютера). Минимальная ширина 320px.
- Учесть: клавиатура на iOS перекрывает поля (скролл к полю при фокусе), `viewportStableHeight`, отключение свайпа закрытия на экранах с drag-and-drop (`disableVerticalSwipes`).
- Роутинг по `startapp`: `e_<id>` → событие, `j_<token>` → запись по ссылке, `i_<id>` → приглашение.

Экраны:

**Онбординг**
1. Выбор ролей (мультивыбор).
2. Минимальный профиль по ролям: комик — сценическое имя, город, контакт; организатор — имя, город. Остальное — «заполните позже».
3. Проверка, что бот запущен; если нет — кнопка «Включить уведомления» (`requestWriteAccess`).

**Комик**
- *Мой календарь* — лента по дням + переключатель «месяц». Карточка: площадка, время, номер в составе, статус, подтверждение на сегодня. Ручные события и занятость — другим цветом.
- *Входящие* — приглашения (принять / отказаться / предложить другое время) и статусы заявок.
- *Ищут комиков* — открытые наборы в моём городе, фильтр по дате и формату. Подать заявку.
- *Событие* — детали, условия, мой статус, состав (если организатор разрешил показывать).
- *Профиль* — редактирование, фото, ссылки.
- *Настройки* — время дайджеста, напоминание перед выходом, буфер на дорогу, доверенные организаторы и правила автопринятия, ссылка на календарь (ICS) + инструкция для iPhone и Google.
- *Занятость* — добавить «занят» или ручное выступление.

**Организатор**
- *Мои события* — предстоящие / прошедшие, черновики.
- *Создание/редактирование события* — все поля из 3.events, выбор/создание площадки, способы набора, копирование из прошлого события.
- *Состав* (главный экран) — вкладки: Состав (drag-and-drop, статус подтверждения на сегодня, присутствие) / Заявки / Приглашения / Резерв. Массовые действия: принять выбранных, в резерв, отклонить. Кнопки: «Пригласить», «Рассылка составу», «Скопировать для афиши», «Опубликовать в чат», «Назначить ведущего».
- *Поиск комиков* — имя, город, категория, «свободен в это время события». Карточка комика: фото, категория, ссылки, количество выступлений через приложение. Пригласить в событие.

**Ведущий**
- *События, где я ведущий* → экран состава в режиме, ограниченном правами.

## 9. API

REST, JSON, префикс `/api/v1`. Схемы запросов/ответов — Zod в `packages/shared`, общие для фронта и бэка.

### Авторизация
- `POST /auth/telegram` — тело: `initData` (raw string). Сервер проверяет HMAC-SHA256 подпись по алгоритму Telegram (ключ = HMAC("WebAppData", bot_token)), отклоняет `auth_date` старше 24 часов, создаёт/обновляет пользователя, возвращает JWT (срок 7 дней).
- Все остальные эндпоинты — `Authorization: Bearer <jwt>`.
- В dev-режиме — флаг `DEV_AUTH=true` разрешает вход по `telegram_id` без подписи. В production этот флаг должен ронять старт приложения.

### Эндпоинты (минимум для MVP)
```

PUT    /me/comedian-profile
```

## 10. Календарная подписка (ICS)

- `GET /cal/:token.ics` — генерировать на лету (библиотека `ical-generator`), `Content-Type: text/calendar; charset=utf-8`.
- Включать: `accepted`-участия (название = «🎤 {event.title} — {venue}», в описании: номер в составе, примерное время выхода, адрес, статус подтверждения), `manual_gig` из `busy_slots`. Окна — примерное время на сцене, но не короче всего события, чтобы в календаре было видно полный вечер (решение: `DTSTART` = начало события, в описании — примерное время выхода).
- Стабильные `UID` (`participation-{id}@standupcalendar`), `SEQUENCE` растёт при изменениях, отменённые — со `STATUS:CANCELLED` ещё 14 дней.
- `X-WR-CALNAME`, `X-WR-TIMEZONE`, `REFRESH-INTERVAL;VALUE=DURATION:PT1H` (клиенты могут игнорировать).
- В Mini App: кнопка «Подписаться» (открывает `webcal://...` через `openLink`), кнопка «Скопировать ссылку», инструкции для iPhone и Google Calendar (в Google подписка по URL добавляется только через веб-версию). Предупредить в UI, что внешние календари обновляются с задержкой, срочное приходит в бот.
- Синхронизация в обратную сторону (чтение личных календарей) — **не делать**.

## 11. Нефункциональные требования

- **Таймзоны:** всё в UTC в базе, отображение в таймзоне площадки (для событий) или пользователя (для дайджестов). Использовать `date-fns-tz` или `Temporal` polyfill. Никаких `new Date().getHours()` в бизнес-логике.
- **Безопасность:** проверка подписи `initData`; права на каждом эндпоинте через `can()`; токены ICS и ссылок — криптостойкие; не логировать токены и `initData`; rate limit на публичных эндпоинтах.
- **Персональные данные:** хостинг на территории РФ (152-ФЗ) — конфигурация через переменные окружения, без привязки к конкретному облаку. Эндпоинт удаления аккаунта (`DELETE /me`) с анонимизацией истории.
- **Логи:** структурированные (pino), request id, без персональных данных в сообщениях об ошибках.
- **Миграции:** только через Drizzle migrations, ни одного ручного изменения схемы.
- **Сиды:** скрипт `pnpm seed` создаёт города, 3 площадки, 2 организаторов, 20 комиков с разными категориями, 5 событий в разных статусах — для разработки и демонстрации.
- **Конфигурация:** `.env.example` со всеми переменными (BOT_TOKEN, BOT_USERNAME, MINIAPP_SHORT_NAME, DATABASE_URL, REDIS_URL, S3_*, JWT_SECRET, PUBLIC_BASE_URL, DEV_AUTH).

## 12. Этапы и критерии приёмки

### Этап 1. Каркас
- Монорепо, docker compose (postgres, redis, minio, api, bot, worker, miniapp), линтер, форматтер, Vitest, CI-скрипт `pnpm check` (lint + typecheck + test).
- Авторизация через `initData` + dev-вход.
- Бот отвечает на `/start` и открывает Mini App.
- **Приёмка:** `docker compose up` → Mini App открывается из бота, пользователь создаётся в БД; тест проверки подписи `initData` (валидная, подделанная, просроченная).

### Этап 2. Профили и справочники
- Роли, онбординг, профиль комика с фото, профиль организатора, города, площадки.
- **Приёмка:** пользователь проходит онбординг за 3 экрана; фото загружаются и ресайзятся; профиль заполняется постепенно.

### Этап 3. Ядро домена
- `packages/domain`: статусы и переходы, права, окна выступлений, пересечения, расчёт времени уведомлений.
- **Приёмка:** покрытие тестами `packages/domain` ≥ 90%; тесты на все разрешённые и запрещённые переходы, на таблицу прав, на пересечения (включая буфер, событие без позиций, переход через полночь, разные таймзоны).

### Этап 4. События и набор
- Создание/редактирование/копирование событий, три способа набора, заявки, приглашения, поиск комиков, экран «Ищут комиков».
- **Приёмка:** организатор создаёт событие и набирает состав всеми тремя способами; комик видит заявку и приглашение во «Входящих»; при пересечении приходит понятное предупреждение.

### Этап 5. Состав
- Экран состава, drag-and-drop, резерв, массовые действия, ведущие с правами, замена из резерва, текст для афиши, рассылка составу.
- **Приёмка:** два пользователя (организатор и ведущий) одновременно меняют порядок → второй получает конфликт версии и актуальный список; ведущий без `can_reorder` не может менять порядок ни из UI, ни через API.

### Этап 6. Уведомления
- `scheduled_notifications`, планировщик, отправитель с троттлингом, все уведомления из 7.2, дайджест с подтверждением, эскалация организатору, кнопки в сообщениях.
- **Приёмка:** интеграционный тест «день выступления» с подменой времени: дайджест → нет ответа → повтор → алерт организатору → «Позвать резерв» → резервист принял и занял позицию. Перенос события на час переносит все pending-уведомления. 403 помечает пользователя как заблокировавшего бота.

### Этап 7. Календарь комика и автопринятие
- Мой календарь (лента + месяц), ручная занятость, правила автопринятия, ICS-подписка.
- **Приёмка:** тест гонки автопринятия (два одновременных приглашения на одно время → принято одно); ICS-файл валиден (проверить парсером) и открывается в Apple Calendar и Google Calendar.

### Этап 8. Посты в чаты и полировка
- Бот в группах, публикация анонсов, обновление постов, `startapp`-роутинг.
- Проход по UI на iOS, Android и Telegram Desktop; пустые состояния; ошибки сети.
- **Приёмка:** анонс публикуется в группу, кнопка открывает Mini App на экране события, комик подаёт заявку за ≤ 3 нажатия от поста (для уже зарегистрированного).

**Итог MVP:** мероприятие полностью организуется через систему — от набора до подтверждения выхода на сцену.

## 13. Вне MVP (не делать, но не мешать)

**Версия 1.0**
- Клубы: организация, участники с ролями, общая афиша, несколько организаторов и ведущих.
- Подписки (Basic / Pro / Организатор / Клуб). Оплата цифровых подписок внутри Mini App — через Telegram Stars (`XTR`, `subscription_period`). Перед реализацией проверить актуальные правила Telegram.
- Повторяющиеся события и шаблоны, история мероприятий, избранное, уведомления о новых наборах.
- Pro: приоритет в поиске, темы оформления, расширенный автопилот.
- Двусторонняя синхронизация с Google Calendar (OAuth) — только если подтвердят, что нужна.

**Версия 2.0**
- Умное расписание: предложения перестановок, если комик выступает в нескольких местах за вечер, с согласованием организаторами.
- Расчёт дороги между площадками: кэш матрицы времени между площадками (self-hosted OSRM или API Яндекс/2ГИС).
- Рекомендации комиков (сначала правила/скоринг, без ML).
- Доступ менеджера к календарю комика (расширение системы прав).
- Генерация афиш из шаблонов (HTML → картинка), лимиты.
- Аналитика: выступления, заявки, подтверждения, отмены, неявки.

Чтобы это не потребовало переписывания: права — через `can()` с расширяемыми ролями; `events` позже получат `club_id` null; поиск комиков — через отдельный сервис-функцию, куда потом добавится ранжирование.

## 14. Открытые вопросы к заказчику

1. Категории комиков (новичок / опытный / медийный): только самоопределение или модерация? Кто модерирует? *(В MVP — самоопределение, поле `category_verified` заложено.)*
2. Видят ли комики полный состав события до его закрытия? *(В MVP — настройка на событии, по умолчанию да.)*
3. «Предложить другое время» — свободный текст или выбор другого события этого организатора? *(В MVP — текст.)*
4. Нужна ли публичная страница профиля комика вне Telegram (веб)?
5. Время дайджеста по умолчанию и порог эскалации организатору (сейчас 10:00 и за 3 часа).
6. Где хостим (РФ, КЗ или оба) и чьи аккаунты: бот, домен, S3.
7. Кто видит статистику неявок и видит ли вообще.
8. Нужна ли выгрузка состава в Excel/CSV.
9. Загрузка фото: ТЗ предлагает presigned upload в S3. *(Сейчас — через API: сервер всё равно делает ресайз и чистит EXIF, а в dev MinIO недоступен с телефона. Переделать на presigned, если нагрузка на API станет заметной.)*
10. Буфер на дорогу при пересечениях: ТЗ говорит «пересечение окон занятости» (сцена ± буфер). Если расширять оба выступления, между площадками нужно 2 × буфер. *(Сейчас буфер учитывается один раз: между двумя выступлениями ≥ buffer минут, с `busy` — просто не пересекаться.)*
11. Если комику дайджест по времени приходится позже начала шоу (утреннее шоу или шоу после полуночи по его таймзоне) — дайджест не шлётся, остаётся напоминание перед выходом. Нужно ли иначе?
