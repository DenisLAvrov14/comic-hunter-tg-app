# Прогресс

## Этап 1. Каркас — в работе (ожидает ручной проверки в Telegram)

Сделано:

- Монорепо pnpm: `apps/{api,bot,worker,miniapp}`, `packages/{db,domain,shared}`. Пакеты экспортируют `.ts` напрямую, сервисы запускаются через `tsx`.
- ESLint 9 (flat config) + Prettier + Vitest. `pnpm check` = lint + format:check + typecheck + test.
- docker compose: postgres 16, redis 7, minio, `migrate` (одноразовый, применяет Drizzle-миграции), api, bot, worker, miniapp (nginx со статикой и прокси `/api` → api).
- БД: таблицы `users`, `user_roles` (первая миграция `packages/db/drizzle/0000_*`).
- API (`/api/v1`):
  - `POST /auth/telegram` — проверка HMAC-SHA256 подписи `initData`, отказ при `auth_date` старше 24 ч, upsert пользователя, JWT на 7 дней; rate limit 30/мин.
  - `POST /auth/dev` — вход по `telegram_id`, регистрируется только при `DEV_AUTH=true`; с `NODE_ENV=production` и `DEV_AUTH=true` API не стартует.
  - `GET /auth/config`, `GET /me`, `GET /health`.
  - Единый формат ошибок `{ error: { code, message, details? } }`, request id, redact `authorization`/`initData` в логах.
- Бот: `/start` → `bot_started = true`, приветствие, web_app-кнопка и кнопка меню (если `MINIAPP_URL` https); `/start <e_|j_|i_...>` → URL-кнопка `t.me/<bot>/<app>?startapp=...`. Polling в dev, webhook в prod. Без `BOT_TOKEN` не падает, а пишет предупреждение.
- Mini App: инициализация `@telegram-apps/sdk-react` v3, тема из `themeParams`, авторизация по `initData`; вне Telegram при `DEV_AUTH` — форма dev-входа.
- Worker: заглушка с тиком (планировщик — этап 6).
- Тесты: проверка `initData` (валидная, подделанная, чужой токен, просроченная, граница срока, мусор), конфиг (`DEV_AUTH` в production), ссылки бота, интеграционные тесты API против Postgres (`TEST_DATABASE_URL`).

Отложено / для приёмки:

- Ручная проверка «Mini App открывается из бота» требует реального `BOT_TOKEN` и https-туннеля (см. README).
- CI-пайплайн (GitHub Actions) не настроен — есть только скрипт `pnpm check`.
- ~~MinIO поднимается, но бакет и S3-клиент — этап 2.~~ Сделано в этапе 2.
- Локально контейнеры запускаются через Podman (`podman compose`); Postgres проброшен на порт 5442.

## Этап 2. Профили и справочники — сделано (кроме проверки в настоящем Telegram)

Проверено: стек поднят через `podman-compose` (см. README); сквозной прогон через nginx :8080 — dev-вход, роли, профиль, загрузка фото, превью 400px отдаётся из MinIO по `/media`; онбординг пройден в headless Chrome (390px) за 3 экрана.

Сделано:

- БД (миграция `0001_*`): `cities` (справочник РФ/КЗ с IANA-таймзонами, синхронизируется после миграций), `comedian_profiles`, `comedian_photos` (оригинал + превью), `organizer_profiles`, `venues` (таймзона берётся из города).
- Домен: `onboardingStep` / `requiredProfiles` — какие профили обязательны для выбранных ролей (ведущему не нужен), с тестами.
- API: `PATCH /me` (таймзона, `writeAccessGranted` → `bot_started`), `PUT /me/roles`, `PUT /me/comedian-profile`, `PUT /me/organizer-profile` (обязательные поля перезаписываются, необязательные — только если переданы → профиль заполняется постепенно), `POST /me/photos`, `DELETE /me/photos/:id`, `GET /cities`, `GET /venues?city`, `POST /venues` (только организатор). При сохранении профиля таймзона пользователя = таймзона города. `GET /me` отдаёт флаг `onboarded`.
- Фото: multipart через API, лимиты 10 шт. и 10 МБ, JPEG/PNG/WebP/HEIC; sharp разворачивает по EXIF, срезает метаданные (геометку), оригинал ≤ 4096px + превью 400px в JPEG. Хранилище — S3/MinIO (`S3Storage`), в тестах — `MemoryStorage`. В dev API сам создаёт бакет и открывает `photos/*` на чтение; Mini App отдаёт фото через прокси `/media` (nginx и vite).
- Mini App: онбординг на 3 экрана — роли (мультивыбор) → минимальный профиль по ролям (комик: имя, город, контакт; организатор: имя, город) → разрешение писать (`requestWriteAccess`, шаг пропускается, если бот уже запущен). Экраны «Профиль комика» (все поля, ссылки, фото), «Профиль организатора», «Площадки» (список города и добавление), «Мои роли». Нативные MainButton/BackButton в Telegram (в браузере — обычные кнопки), хаптика, прокрутка поля при фокусе (iOS).
- Сид `pnpm seed`: города, 3 площадки, 2 организатора, 20 комиков.
- Тесты: интеграционные сценарии онбординга, постепенного заполнения профиля, валидации, загрузки фото с проверкой превью 400px, площадок и прав на их создание.

Отложено:

- Загрузка фото идёт через API, а не presigned upload (см. SPEC §14, вопрос 9).
- Права пока проверяются по ролям напрямую (`TODO(stage 3)`), на этапе 3 — через `can()`.
- 5 событий в сиде — на этапе 4, когда появится таблица `events`.
- Сортировка фото перетаскиванием — не делали, порядок = порядок загрузки.

## Этап 3. Ядро домена — сделано

Сделано (всё в `packages/domain`, без I/O):

- `participation.ts` — статусы, одна таблица переходов `TRANSITIONS`, `transition(current, action, actor)`; `initialStatus`, `isActive`, `hasFreeSlot`, `compactPositions` (уплотнение позиций), `nextPosition`, `applyOrder` (новый порядок = перестановка текущего состава).
- `permissions.ts` — `can(user, action, resource)` по таблице SPEC §5; флаги ведущего — открытый `Record`, чтобы права клубов добавлялись без изменения логики; `defaultHostPermissions`.
- `slots.ts` — `eventWindow`, `computeSlotWindows` (окна по позициям, без позиции — всё событие), `expand`, `overlaps`, `findConflicts` (буфер для выступлений и `manual_gig`, без буфера для `busy`, результат с указанием, с чем пересекается).
- `notifications.ts` — типы уведомлений, `planDayNotifications` (дайджест в `digest_time` по таймзоне комика или сразу, если время прошло; повтор +2 ч; алерт организатору за 3 ч; напоминание за N минут до выхода), `dedupeKey`, `retryDelayMs`.
- Тесты: все разрешённые и все запрещённые переходы (перебор статус × действие × актор), вся таблица прав, пересечения (буфер, событие без позиций, полночь, разные таймзоны), уведомления (Москва, Калининград, Новосибирск, Алматы, Владивосток, полночь, позднее принятие, перенос события).
- Покрытие: `pnpm test:coverage` — 100% строк, 99% веток; порог 90% зашит в `vitest.config.ts`.

Решения, вынесенные в SPEC §14: буфер учитывается один раз (вопрос 10), дайджест не шлётся, если его время позже начала шоу (вопрос 11).

Отложено:

- `pg_advisory_xact_lock`, `tstzrange`/GiST и `rescheduleFor*` — это I/O, появятся вместе с таблицами на этапах 4, 6 и 7.

## Этап 4. События и набор — сделано

Сделано:

- БД (миграция `0002_*`): `events` (+ `window_ends_at` — конец окна события для поиска пересечений, `show_lineup`), `participations`, `participation_events` (история каждого перехода), `event_staff`, `busy_slots`. GiST-индексы по `tstzrange` для событий и занятости.
- Домен: `time.ts` — местное время площадки ↔ UTC, сдвиг на N дней с сохранением местного времени.
- API: `GET /events` (открытые наборы города, фильтр по дате и формату), `GET /me/events`, `POST /events` (время вводится по таймзоне площадки), `GET/PATCH /events/:id`, `POST /events/:id/cancel`, `POST /events/:id/duplicate` (черновик через неделю), `GET /events/by-link/:token`, `POST /events/:id/link/rotate`, `POST /events/:id/applications` (открытый набор или токен ссылки), `POST /events/:id/invitations`, `GET /events/:id/lineup`, `POST /participations/:id/actions`, `GET /me/inbox`, `GET /comedians` (имя, город, категория, «свободен во время события»), `GET /comedians/:id`. `/auth/config` отдаёт `botUsername`/`miniAppShortName` для ссылок.
- Действия над участием — одна транзакция: `FOR UPDATE` на событие, `transition()` из домена, проверка мест (`LINEUP_FULL`), пересечений (`CONFLICT_SCHEDULE` со списком «с чем пересекается»; организатор может принять с `force`), advisory-lock на комика, уплотнение позиций, история, `lineup_version`.
- Mini App: «Ищут комиков», карточка события (заявка, запись по ссылке `/join/:token`, отказ), «Входящие» (принять / отказаться / предложить другое, предупреждение о пересечении с «Принять всё равно»), «Мои события», создание и редактирование события, управление набором (вкладки Состав / Заявки / Приглашения / Резерв, действия, ссылка для записи, копия, отмена), приглашение комиков с поиском. Роутинг `startapp`: `e_` → событие, `j_` → запись по ссылке, `i_` → входящие (в том числе после онбординга).
- Тесты: интеграционные — три способа набора, входящие, состав и позиции, пересечение и принятие вопреки, `LINEUP_FULL`, резерв и повышение, права, встречное предложение с историей, **гонка двух параллельных принятий (принято одно)**, поиск «свободен в это время», копия и отмена. Сценарий пройден в headless Chrome на демо-данных.

Отложено:

- Уведомления о переходах (`TODO(stage 6)`), автопринятие (`TODO(stage 7)`).
- Ссылка для записи в UI появится после регистрации Mini App в BotFather (`MINIAPP_SHORT_NAME`).
- Перестановка порядка, массовые действия, ведущие, замена из резерва — этап 5.
- При изменении времени события пересечения у состава пока не перепроверяются (этап 6, вместе с `rescheduleForEvent`).
