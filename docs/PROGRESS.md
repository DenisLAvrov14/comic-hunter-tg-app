# Прогресс

## Этап 1. Каркас — в работе (ожидает ручной проверки в Telegram)

Сделано:

- Монорепо pnpm: `apps/{api,bot,worker,miniapp}`, `packages/{db,domain,shared}`. Пакеты экспортируют `.ts` напрямую, сервисы запускаются через `tsx`.
- ESLint 9 (flat config) + Prettier + Vitest. `pnpm check` = lint + format:check + typecheck + test.
- docker compose: postgres 16, redis 7, minio, `migrate` (одноразовый, применяет Drizzle-миграции), api, bot, worker, miniapp (nginx со статикой и прокси `/api` → api).
- БД: таблицы `users`, `user_roles` (первая миграция `packages/db/drizzle/0000_*`).
- API (`/api/v1`):
  - `POST /auth/telegram` — проверка HMAC-SHA256 подписи `initData`, отказ при `auth_date` старше 24 ч, upsert пользователя, JWT на 7 дней; rate limit 30/мин.
  - `POST /auth/dev` — вход по `telegram_id`, регистрируется только при `DEV_AUTH=true`; с `NODE_ENV=production` и `DEV_AUTH=true` API не стартует.
  - `GET /auth/config`, `GET /me`, `GET /health`.
  - Единый формат ошибок `{ error: { code, message, details? } }`, request id, redact `authorization`/`initData` в логах.
- Бот: `/start` → `bot_started = true`, приветствие, web_app-кнопка и кнопка меню (если `MINIAPP_URL` https); `/start <e_|j_|i_...>` → URL-кнопка `t.me/<bot>/<app>?startapp=...`. Polling в dev, webhook в prod. Без `BOT_TOKEN` не падает, а пишет предупреждение.
- Mini App: инициализация `@telegram-apps/sdk-react` v3, тема из `themeParams`, авторизация по `initData`; вне Telegram при `DEV_AUTH` — форма dev-входа.
- Worker: заглушка с тиком (планировщик — этап 6).
- Тесты: проверка `initData` (валидная, подделанная, чужой токен, просроченная, граница срока, мусор), конфиг (`DEV_AUTH` в production), ссылки бота, интеграционные тесты API против Postgres (`TEST_DATABASE_URL`).

Отложено / для приёмки:

- Ручная проверка «Mini App открывается из бота» требует реального `BOT_TOKEN` и https-туннеля (см. README).
- CI-пайплайн (GitHub Actions) не настроен — есть только скрипт `pnpm check`.
- ~~MinIO поднимается, но бакет и S3-клиент — этап 2.~~ Сделано в этапе 2.
- Локально контейнеры запускаются через Podman (`podman compose`); Postgres проброшен на порт 5442.

## Этап 2. Профили и справочники — сделано (кроме проверки в настоящем Telegram)

Проверено: стек поднят через `podman-compose` (см. README); сквозной прогон через nginx :8080 — dev-вход, роли, профиль, загрузка фото, превью 400px отдаётся из MinIO по `/media`; онбординг пройден в headless Chrome (390px) за 3 экрана.

Сделано:

- БД (миграция `0001_*`): `cities` (справочник РФ/КЗ с IANA-таймзонами, синхронизируется после миграций), `comedian_profiles`, `comedian_photos` (оригинал + превью), `organizer_profiles`, `venues` (таймзона берётся из города).
- Домен: `onboardingStep` / `requiredProfiles` — какие профили обязательны для выбранных ролей (ведущему не нужен), с тестами.
- API: `PATCH /me` (таймзона, `writeAccessGranted` → `bot_started`), `PUT /me/roles`, `PUT /me/comedian-profile`, `PUT /me/organizer-profile` (обязательные поля перезаписываются, необязательные — только если переданы → профиль заполняется постепенно), `POST /me/photos`, `DELETE /me/photos/:id`, `GET /cities`, `GET /venues?city`, `POST /venues` (только организатор). При сохранении профиля таймзона пользователя = таймзона города. `GET /me` отдаёт флаг `onboarded`.
- Фото: multipart через API, лимиты 10 шт. и 10 МБ, JPEG/PNG/WebP/HEIC; sharp разворачивает по EXIF, срезает метаданные (геометку), оригинал ≤ 4096px + превью 400px в JPEG. Хранилище — S3/MinIO (`S3Storage`), в тестах — `MemoryStorage`. В dev API сам создаёт бакет и открывает `photos/*` на чтение; Mini App отдаёт фото через прокси `/media` (nginx и vite).
- Mini App: онбординг на 3 экрана — роли (мультивыбор) → минимальный профиль по ролям (комик: имя, город, контакт; организатор: имя, город) → разрешение писать (`requestWriteAccess`, шаг пропускается, если бот уже запущен). Экраны «Профиль комика» (все поля, ссылки, фото), «Профиль организатора», «Площадки» (список города и добавление), «Мои роли». Нативные MainButton/BackButton в Telegram (в браузере — обычные кнопки), хаптика, прокрутка поля при фокусе (iOS).
- Сид `pnpm seed`: города, 3 площадки, 2 организатора, 20 комиков.
- Тесты: интеграционные сценарии онбординга, постепенного заполнения профиля, валидации, загрузки фото с проверкой превью 400px, площадок и прав на их создание.

Отложено:

- Загрузка фото идёт через API, а не presigned upload (см. SPEC §14, вопрос 9).
- Права пока проверяются по ролям напрямую (`TODO(stage 3)`), на этапе 3 — через `can()`.
- 5 событий в сиде — на этапе 4, когда появится таблица `events`.
- Сортировка фото перетаскиванием — не делали, порядок = порядок загрузки.

## Этап 3. Ядро домена — сделано

Сделано (всё в `packages/domain`, без I/O):

- `participation.ts` — статусы, одна таблица переходов `TRANSITIONS`, `transition(current, action, actor)`; `initialStatus`, `isActive`, `hasFreeSlot`, `compactPositions` (уплотнение позиций), `nextPosition`, `applyOrder` (новый порядок = перестановка текущего состава).
- `permissions.ts` — `can(user, action, resource)` по таблице SPEC §5; флаги ведущего — открытый `Record`, чтобы права клубов добавлялись без изменения логики; `defaultHostPermissions`.
- `slots.ts` — `eventWindow`, `computeSlotWindows` (окна по позициям, без позиции — всё событие), `expand`, `overlaps`, `findConflicts` (буфер для выступлений и `manual_gig`, без буфера для `busy`, результат с указанием, с чем пересекается).
- `notifications.ts` — типы уведомлений, `planDayNotifications` (дайджест в `digest_time` по таймзоне комика или сразу, если время прошло; повтор +2 ч; алерт организатору за 3 ч; напоминание за N минут до выхода), `dedupeKey`, `retryDelayMs`.
- Тесты: все разрешённые и все запрещённые переходы (перебор статус × действие × актор), вся таблица прав, пересечения (буфер, событие без позиций, полночь, разные таймзоны), уведомления (Москва, Калининград, Новосибирск, Алматы, Владивосток, полночь, позднее принятие, перенос события).
- Покрытие: `pnpm test:coverage` — 100% строк, 99% веток; порог 90% зашит в `vitest.config.ts`.

Решения, вынесенные в SPEC §14: буфер учитывается один раз (вопрос 10), дайджест не шлётся, если его время позже начала шоу (вопрос 11).

Отложено:

- `pg_advisory_xact_lock`, `tstzrange`/GiST и `rescheduleFor*` — это I/O, появятся вместе с таблицами на этапах 4, 6 и 7.

## Этап 4. События и набор — сделано

Сделано:

- БД (миграция `0002_*`): `events` (+ `window_ends_at` — конец окна события для поиска пересечений, `show_lineup`), `participations`, `participation_events` (история каждого перехода), `event_staff`, `busy_slots`. GiST-индексы по `tstzrange` для событий и занятости.
- Домен: `time.ts` — местное время площадки ↔ UTC, сдвиг на N дней с сохранением местного времени.
- API: `GET /events` (открытые наборы города, фильтр по дате и формату), `GET /me/events`, `POST /events` (время вводится по таймзоне площадки), `GET/PATCH /events/:id`, `POST /events/:id/cancel`, `POST /events/:id/duplicate` (черновик через неделю), `GET /events/by-link/:token`, `POST /events/:id/link/rotate`, `POST /events/:id/applications` (открытый набор или токен ссылки), `POST /events/:id/invitations`, `GET /events/:id/lineup`, `POST /participations/:id/actions`, `GET /me/inbox`, `GET /comedians` (имя, город, категория, «свободен во время события»), `GET /comedians/:id`. `/auth/config` отдаёт `botUsername`/`miniAppShortName` для ссылок.
- Действия над участием — одна транзакция: `FOR UPDATE` на событие, `transition()` из домена, проверка мест (`LINEUP_FULL`), пересечений (`CONFLICT_SCHEDULE` со списком «с чем пересекается»; организатор может принять с `force`), advisory-lock на комика, уплотнение позиций, история, `lineup_version`.
- Mini App: «Ищут комиков», карточка события (заявка, запись по ссылке `/join/:token`, отказ), «Входящие» (принять / отказаться / предложить другое, предупреждение о пересечении с «Принять всё равно»), «Мои события», создание и редактирование события, управление набором (вкладки Состав / Заявки / Приглашения / Резерв, действия, ссылка для записи, копия, отмена), приглашение комиков с поиском. Роутинг `startapp`: `e_` → событие, `j_` → запись по ссылке, `i_` → входящие (в том числе после онбординга).
- Тесты: интеграционные — три способа набора, входящие, состав и позиции, пересечение и принятие вопреки, `LINEUP_FULL`, резерв и повышение, права, встречное предложение с историей, **гонка двух параллельных принятий (принято одно)**, поиск «свободен в это время», копия и отмена. Сценарий пройден в headless Chrome на демо-данных.

## Этап 5. Состав — сделано

Сделано:

- Домен: срочный вызов из резерва — резервист с `is_urgent` сам принимает (`reserve → accepted`) или отказывается (остаётся в резерве); обычный резервист сам в состав не попадает.
- БД (миграция `0003_*`): `participations.replacement_for` — кого заменяет позванный резервист.
- API: `PATCH /events/:id/lineup/order` (оптимистическая блокировка по `lineup_version` → `409 VERSION_MISMATCH` с актуальной версией), `POST /participations/:id/attendance`, `POST /events/:id/replacement` (срочный вызов выбранных резервистов; первый согласившийся занимает позицию выбывшего, выбывший → `removed`, остальные вызовы закрываются), `POST /events/:id/broadcast`, `GET /events/:id/poster-text`, `PUT/DELETE /events/:id/staff/:userId`, `GET /hosts`, `GET /me/hosting`. Все проверки — через `can()` с флагами ведущего.
- Отправка сообщений из API — интерфейс `MessageSender` (Bot API напрямую; без токена и в тестах — в памяти). 403 от Telegram ставит `users.bot_blocked`.
- Текст для афиши — шаблон в i18n, сборка чистой функцией с тестами.
- Mini App: экран состава для организатора и ведущего (кнопки по правам): drag-and-drop (`@dnd-kit`, тач и мышь, «ручка»), опрос каждые 5 с, сообщение о конфликте версии с перезагрузкой, массовые действия по заявкам, присутствие, статус подтверждения дня, замена из резерва (без пересечений — сверху), «Скопировать для афиши», рассылка, назначение ведущих и их права, «Я веду». Вертикальный свайп закрытия Mini App на экране состава отключён. Срочный вызов на замену виден резервисту во «Входящих».
- Тесты: **организатор и ведущий меняют порядок одновременно → второй получает 409 и актуальный список; ведущий без `can_reorder` получает 403 через API**; присутствие; замена (опоздавший резервист получает `INVALID_TRANSITION`); рассылка с пометкой заблокировавшего; афиша; снятие ведущего. Перетаскивание и режим ведущего проверены в headless Chrome.

Отложено:

- Рассылка и срочный вызов уходят из API напрямую, без очереди и ретраев — на этапе 6 переедут в `scheduled_notifications` + BullMQ.
- Подтверждение участия в день выступления (`day_confirmation`) показывается, но выставляется ботом — этап 6.

## Этап 6. Уведомления — сделано (кроме проверки на живом Telegram-аккаунте)

Сделано:

- БД (миграция `0004_*`): `scheduled_notifications` (статусы `pending → queued → sent | cancelled | failed`, `dedupe_key` unique, `payload`, `attempts`, `last_error`), у `users` — `digest_time` и `pre_show_minutes`.
- Домен: `noticesForTransition` — какое уведомление и кому порождает каждый переход (с тестами).
- `packages/notify` (общий для API, бота и worker):
  - `schedule.ts` — идемпотентный upsert по `dedupe_key` (ожидающее переносится, отправленное не трогается); `rescheduleForParticipation/Event/User`; уведомления о переходах, о переносе и отмене события, о смене позиции (не чаще раза в 5 минут), «новые заявки» (не чаще раза в 15 минут на событие), срочный вызов и рассылка.
  - `render.ts` — текст собирается в момент отправки из актуальных данных; неактуальное (подтвердил, событие отменено, нет выступлений, бот недоступен) отменяется с причиной. Один дайджест на комика в день со всеми выступлениями и парой кнопок на каждое; если приняли после отправки дайджеста — отдельный дайджест сразу.
  - `deliver.ts` — `claimDue` (`FOR UPDATE SKIP LOCKED`, зависшие `queued` забираются повторно), отправка с разбором ответа: 403 → `users.bot_blocked` и `failed`; 429 → отложить на `retry_after`; прочие ошибки → экспоненциальные ретраи до 6 попыток.
- Worker: планировщик раз в минуту ставит созревшие уведомления в BullMQ (`jobId` = id уведомления — без дублей); отправитель с лимитом 25 сообщений/с суммарно и 1 сообщение/с в чат (через Redis), отложенные задачи вместо падений.
- API: `POST /participations/:id/day-confirmation`, `POST /participations/:id/call-reserve` (зовёт резервистов без пересечений), `PATCH /me` (время дайджеста, напоминание), рассылка и срочный вызов теперь через очередь. Внутренний вход `POST /internal/as-user` для бота по `INTERNAL_TOKEN` (nginx его наружу не пропускает).
- Бот: кнопки «Подтверждаю / Не смогу», «Принять / Отказаться» (приглашение и срочная замена), «Позвать резерв» — выполняются через API от имени пользователя (те же проверки прав); после ответа кнопки убираются. Команды `/today` и `/settings`.
- Mini App: экран «Уведомления» (время дайджеста, напоминание перед выходом, включить бота), подтверждение участия в карточке события за сутки до начала.
- Тесты: **интеграционный «день выступления» с подменой времени** — дайджест в 10:00 → повтор в 12:00 → алерт организатору в 17:00 → «Позвать резерв» → резервист принял и занял позицию, выбывшей — «убрали из состава»; **перенос события на час переносит pending-уведомления** (дайджест остаётся в 10:00), отмена отменяет; один дайджест на два выступления; «Не смогу» → алерт организатору; **403 помечает пользователя**; внутренний вход только с секретом. Разбор `callback_data` в боте.

## Этап 7. Календарь комика и автопринятие — сделано (кроме проверки в Apple/Google Calendar)

Сделано:

- Домен: `autoAccept.ts` — `checkRule` (формат, день недели и окно времени по таймзоне площадки, окно через полночь, лимит выступлений в день), с тестами.
- БД (миграция `0005_*`): `auto_accept_rules` (одно правило на пару комик — организатор), `calendar_feeds`.
- Автопринятие при приглашении (SPEC §6.2): правило → проверка условий → свободное место → пересечения (вопреки пересечению — никогда); шаги идут под `pg_advisory_xact_lock` на комика в транзакции приглашения. Принятое — с `auto_accepted = true` и меткой у организатора; иначе приглашение остаётся, а в сообщении комику — почему автопринятие не сработало. Выключение правила не отменяет принятое.
- API: `GET /me/calendar` (выступления с окном на сцене + занятость), `POST/DELETE /me/busy-slots` (время по таймзоне пользователя), `GET /me/auto-accept-rules`, `PUT/DELETE /me/auto-accept-rules/:organizerId`, `GET /organizers`, `GET /me/calendar-feed`, `POST /me/calendar-feed/rotate`, публичный `GET /cal/:token.ics` (rate limit; nginx проксирует `/cal/`).
- ICS (`ical-generator`): `X-WR-CALNAME`, `X-WR-TIMEZONE`, `REFRESH-INTERVAL`; `DTSTART` — начало события, в описании номер, примерное время выхода, адрес, статус подтверждения; стабильные `UID`, `SEQUENCE` растёт при изменениях; снятые и отменённые — `STATUS:CANCELLED` ещё 14 дней; ручные выступления — отдельными событиями.
- Mini App: «Мой календарь» (лента на 60 дней и месяц с точками; ручная занятость и свои выступления другим цветом; добавление и удаление занятости), в «Уведомлениях» — доверенные организаторы с правилами и подписка на календарь (webcal, копирование, инструкции для iPhone и Google, предупреждение о задержке, перевыпуск ссылки).
- Тесты: **гонка автопринятия — два одновременных приглашения на одно время → принято ровно одно** (5 прогонов подряд); условия правила; календарь и занятость (занятость блокирует автопринятие); **ICS проверяется парсером `ical.js`** (UID, SEQUENCE, CANCELLED, описание); перевыпуск ссылки.

Отложено:

- Проверка подписки в Apple Calendar и Google Calendar на устройствах — нужен публичный https-адрес (`PUBLIC_BASE_URL`), см. README.
- SPEC §14, вопрос 12: `webcal://` через `openLink`.

## Этап 8. Посты в чаты и полировка — код готов, приёмка требует живого Telegram

Сделано:

- БД (миграция `0006_*`): `telegram_chats`, `event_posts` (один пост события на чат).
- Бот: `my_chat_member` — бота добавили в группу/канал (запоминаем, кто добавил), изменили права или удалили; право публикации: в группе — участник или админ, в канале — админ с `can_post_messages` (с тестами).
- `packages/notify/posts.ts`: анонс (название, дата и время по таймзоне площадки, площадка, формат, организатор, условия, статус набора) с URL-кнопкой на прямую ссылку `t.me/<bot>/<app>?startapp=e_<id>` — в группах web_app-кнопки не работают. Повторная публикация в тот же чат редактирует пост.

- Путь комика от поста: кнопка → Mini App на карточке события → «Подать заявку» — 2 нажатия для зарегистрированного.
- Тесты: публикация только в свои чаты с правами, текст и URL-кнопка `startapp`, обновление вместо дубля, «Набор закрыт» после заполнения состава, отмена, права.
